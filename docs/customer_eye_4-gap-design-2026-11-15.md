# customer_eye_4 設計：前の出力がカスだった理由と、このテーマでの埋め方（2026-11-15）

## 前のリサーチャー出力がカスだった実測（2026-11-11 点検、am_owners 171社）

- 記載URLの26%（33件）が他社のサイトだった
- 保有設備の欄は171行すべて空。装置の証拠が0件の会社が16社
- 営業に渡した139社にも証拠0件が7社、「株式会社ソディック様」のような実在しない名前が混入
- 「証拠件数」は保有の証拠ではなく、言及・引用の回数だった（上限60で頭打ち）

## 失敗の型（5つ）

1. **文字列＝会社**：社名の文字列で全工程が回り、会社そのものを同定する工程がない。第2段の「照合」は「その文字列がページに出るか」で、循環していた。同名異社は有名な方に吸着した（フジ→放送持株会社）。
2. **共起＝証拠**：汎用語が両方の条件を満たし、「金属3Dプリンタと書かれた文に出た組織」は全部「保有者」になった。
3. **スニペット証拠化**：ページを開く前に、検索結果の題名と抜粋を証拠にした。
4. **捨てない設計**：不明なものも全量が下流に流れ、「数を水増ししない」という指示と実装が矛盾した。
5. **属性の写し**：着地した（間違った）会社のページから事業内容・住所を写したので、混同がそのまま「事実」になった。

## 本来あるべき姿（田村の仕様と品質指示から）

- 単位は文字列ではなく、統計の区分・団体の名簿・実在のプラットフォーム／イベントなど、一次情報にアンカーのあるものにする
- 数字は出典URLと原文つきで取り、複数ソースで突き合わせる。1ソースだけの数字は確定にしない
- 生成と検証を分ける。自己検証（着地・充足・出典の抜き取り照合・金額のレート確認）を報告の条件にする
- 成果物は引用の束ではなく、突き合わせた表と、事実と分けた推し量りの結論
- 分からないものは「足りない」と書き、根拠のない数字は作らない

## このテーマ（customer_eye_a〜d）での対応

| 失敗の型 | このテーマでの設計 |
|---|---|
| 文字列＝会社・循環照合 | 行（単位）は顧客像の母集団そのもの：統計区分に沿った業種（A）、公式ページで実在を確認済みのイベントと登壇者・出展枠（B）、実在のクラファン基盤とプロジェクト種別（C）、官庁・業界団体の統計対象（D）。会社名の断片から単位を発明する工程を入れない |
| 共起＝証拠 | 証拠の区分を項目1〜9に分け、区分ごとに「その項目に答える行だけが入る」キーワードにした。汎用語の共起では入らない。数字の抽出は figure_patterns で項目別に行い、summary に並ぶ数字は出典区分つきにする |
| スニペット証拠化 | 一次情報に寄せた external_queries（政府統計・官庁・業界団体・公式イベントページ・基盤の公式プロジェクトページ）を先頭に置き、ページ本文から取る設定（limits.pages）を維持する |
| 捨てない設計 | 取れなかった区分は空のまま残る。それが項目10（顧客に聞く質問）の生成材料になる。空を推測で埋める設計にしない |
| 属性の写し | 行ごとに文脈（どの母集団の、どの条件の単位か）を inputs に明記し、別単位の数字が混ざる余地を減らす |

## 機械では埋まらない残り（第2段として Issue #3 に固定済み）

- 複数ソースの突き合わせと、○△×の判定（○は複数ソースが一致したときだけ）
- 推し量った結論（事実と分けて、根拠つきで）
- 項目10の質問の生成
- 自己検証の実施と数字つきの報告
